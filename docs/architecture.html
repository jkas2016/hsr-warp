HSR 워프 — 아키텍처

자가 호스팅 호요버스 스타레일 워프(가챠) 기록 추적기 · 단일 Go 실행파일 + 브라우저 분석

레포 docs/architecture.html · 소스와 CLAUDE.md·docs/ARCHITECTURE.md를 읽고 재구성

게임 캐시에서 authkey를 추출해 비공식 getGachaLog API를 증분 호출하고, 데이터를 SRGF v1.0 형식으로 월별 저장한 뒤, 같은 exe에 내장된 대시보드를 로컬 HTTP로 서빙하고 진행 상황을 SSE로 스트리밍한다. 천장·운·50/50 등 분석은 전부 브라우저의 web/analyze.js가 담당한다. 모든 처리는 로컬에서만 일어난다.

파일별 코드 줄 수

권장 탐색 순서

바깥에서 안으로, 흐름을 따라 읽으면 가장 빠르다.

  1. main.go — 진입점. baseDir, 로깅, 빈 포트 선택, 자산 embed, 브라우저 오픈.
  2. internal/server/server.go — 라우팅과 handleFetch(SSE 오케스트레이션). 전체 흐름의 허브.
  3. internal/collector/cache.go → fetch.go — authkey 추출 후 증분 수집.
  4. internal/store/store.go + srgf.go — 비파괴 월별 저장과 ID 정밀 비교.
  5. web/analyze.js — 모든 분석. 50/50 판정의 단일 소스.
  6. web/dashboard.html — 분석 결과를 차트·표로 렌더.

패키지 구조

Go 모듈 hsr-warp. 의존 방향은 한쪽이다: main → server → {collector, store} (collector도 store 타입에 의존).

패키지 / 파일책임핵심 심볼
main.go 실행파일 기준 baseDir 결정, data/·config.json 경로, 빈 포트 탐색, web/ 자산 embed, 기본 브라우저 자동 오픈, 로깅 셋업. setupLogging, freeListener, stackHandler, fatal
internal/server HTTP 라우팅과 핸들러. 임베드된 web/를 정적 서빙. 패닉 복구 미들웨어로 라우터 전체를 감쌈. Handler, handleFetch, handleData, handleConfig, handleDetect, recoverMiddleware
internal/collector 게임 캐시 data_2에서 정규식으로 authkey URL 추출 → 배너별 페이지네이션으로 저장분보다 최신인 기록만 증분 수집. FindAuthContext, parseAuthURL, FetchIncremental, latestVersion
internal/store SRGF 타입과 저장. 월별 병합·중복제거·정렬, 증분 기준 산출, 비파괴 부분 재작성, 큰 정수 ID 비교. LoadAll, MaxIDByBanner, WriteAffectedMonths, idLess, TZForRegion
web/analyze.js 의존성 0의 순수 분석. 천장·운·50/50·월별. UMD 패턴이라 브라우저와 Node(테스트) 양쪽에서 동작. analyze, analyzeBanner, wasPickup, monthly
참고: tools/genicon은 go:generate 빌드 도구로 런타임 바이너리에 포함되지 않는다.

  1. 브라우저가 게임 경로를 붙여 GET /api/fetch SSE 연결.
  2. FindAuthContext가 StarRail_Data\webCaches\<버전>\Cache\Cache_Data\data_2를 읽어 authkey URL 추출. 버전 폴더는 숫자 비교(latestVersion)로 최신 선택.
  3. LoadAll + MaxIDByBanner로 배너별 마지막 저장 ID(증분 기준선)를 구한다.
  4. FetchIncremental이 배너 1·2·11·12 순으로 페이지네이션, 저장분보다 최신 id만 모은다. 페이지마다 progress SSE, 호출 간 400ms 지연(레이트 리밋 회피).
  5. WriteAffectedMonths가 신규가 생긴 월 파일만 병합·재작성(나머지 월 보존).
  6. LoadAll로 전체 합본을 재구성해 done 이벤트에 요약 + 데이터를 실어 보낸다. 브라우저가 analyze.js로 분석·렌더.

SSE를 쓰는 이유 조회는 배너 4개 × 여러 페이지 × 400ms 지연이라 수초~수십초가 걸린다. 단일 응답 대신 페이지 단위 진행률을 흘려 "멈춘 게 아니다"를 보여주고, authkey 만료 같은 실패도 error 이벤트로 즉시 전달한다.

50/50 픽승·픽뚫

코드만 봐선 가장 이해하기 어려운 부분이자 정확도의 핵심. web/analyze.js가 유일한 판정 소스다.

판정 방식: "그 시점 픽업이었나"

5★를 획득한 시각에 그 item_id가 당시 픽업(rate-up)이었으면 픽승(win), 아니면 픽뚫(loss). 픽뚫이면 다음 5★를 확정(guaranteed)으로 만든다. analyzeBanner가 ID 오름차순(=시간순)으로 순회하며 상태 기계처럼 처리한다.

왜 "풀 소속"이 아니라 "그 시점"인가

"이 캐릭터가 상시풀 소속인가"로 판정하면 틀린다. 패배 풀은 시변적이고 플레이어별이라 구조적으로 불가능하다. 대신 "획득 시각이 그 item의 픽업 기간 근처였나"로 보면 상시풀 편입·Celestial Invitation·콜라보·리런을 모두 자연히 올바르게 처리한다. 같은 캐릭터라도 자기 픽업 배너 때 뽑혔으면 픽승, 한참 뒤 상시풀에서 나왔으면 픽뚫로 갈린다.

±60일 허용오차

SCHEDULE의 날짜는 정확한 일정이 아니라 42일 cadence 근사값이다(3.1=2025-02-25 앵커). 그래서 wasPickup은 획득 시각이 픽업 기간의 ±60일(MATCH_TOL) 안이면 같은 배너로 인정한다. 이 오차는 cadence 날짜 오차는 흡수하면서, 리런·표준 편입 간격(보통 수개월)보다는 작아 오판하지 않는다.

신규 패치 출시 시 SCHEDULE 배열에 {s, e, c, l}을 추가한다 — s/e=기간, c=캐릭터 픽업 item_id, l=광추 픽업 item_id. 누락하면 그 기간 5★는 unidentified(미확인)로 표시되어 "패치 미반영" 신호 역할을 한다.

authkey 추출

게임은 인게임 전언 기록을 열 때 authkey가 박힌 URL을 웹 캐시 data_2에 남긴다. 캐시에는 HoYoLAB·이벤트용 URL이 섞여 있어 getGachaLog 엔드포인트만 골라야 하고, 같은 캐시에 여러 개가 쌓일 수 있으므로 URL의 timestamp 쿼리값이 가장 큰(가장 최근 발급) 것을 채택한다.

  • API 호스트·경로를 하드코딩하지 않고 캐시의 실제 값을 그대로 쓴다 — HoYo가 경로를 바꿔도 견딘다.
  • 쿼리는 자동 파싱 대신 직접 분해해 원본 인코딩(authkey의 %2B 등)을 보존한다. 페이지네이션 키만 떼어낸다.
  • 채택한 URL의 timestamp = "전언 기록을 마지막으로 연 시각" → 만료 진단에 경과 일수로 활용.
authkey 만료 (retcode -101) 게임을 켜는 것만으로는 authkey가 갱신되지 않는다. 게임 안에서 [전언]→[기록] 화면을 실제로 열어야 캐시에 새 authkey가 기록된다(~24시간 유효). 만료 시 경과 일수를 곁들인 안내가 error SSE로 전달된다 — 설계된 동작이다. 레이트 리밋(-110)은 "1~2분 기다리라"는 별도 메시지.

불변식

저장은 비파괴 부분 재작성

WriteAffectedMonths는 이번 조회로 신규가 생긴 월 파일만 로드·병합·중복제거·정렬해 원자적으로 (.tmp 쓰고 rename) 재작성하고, 손대지 않은 월은 보존한다. authkey가 최근 기록만 줄 때 과거 월이 통째로 사라지는 사고를 막는 핵심 보장이며, TestWriteAffectedMonths_PreservesUntouchedMonths가 강제한다.

ID는 큰 정수 — JS는 BigInt 필수

워프 ID는 19자리 정수다(실제 예: 1780207800000106679 ≈ 1.78×1018). 이는 JS의 안전 정수 한계 Number.MAX_SAFE_INTEGER(253−1 ≈ 9.0×1015)를 세 자릿수 가까이 초과하므로, Number로 비교하면 정밀도가 깨진다 — JS는 BigInt로만 비교한다(byId). Go는 일관성을 위해 math/big.Int(idLess)를 쓴다.

analyze.js는 단일 소스

web/analyze.js가 분석의 유일 소스다. 서버가 /analyze.js로 서빙하고 exe에 임베드한다. UMD 패턴으로 브라우저와 Node 양쪽에서 동작하며 의존성 0이어야 한다. web/analyze.test.js가 같은 파일을 require해 검증한다.

로깅

표준 log/slog(JSON, 외부 의존 0). setupLogging이 콘솔 + 날짜별 파일에 동시 출력.

  • 레벨 우선순위 HSRWARP_LOG(런타임) > 빌드 시 박힌 logLevel(ldflags) > 기본 info. release=info, npm run build:debug는 debug를 박은 별도 hsr-warp-debug.exe.
  • 에러엔 항상 스택 stackHandler가 ERROR 이상에 고루틴 스택을 자동 첨부 — 호출부에서 깜빡할 여지가 없다.
  • 전역 패닉 복구 Go엔 전역 예외 핸들러가 없어 recoverMiddleware가 HTTP 핸들러 전체를 감싸 panic을 500 + ERROR로 복구한다.
  • 자격증명 보호 authkey는 절대 로그에 넣지 않는다 — host/path/region/lang/발급시각/개수만.

함정

  • authkey는 전언 기록 화면을 최근 ~24시간 내 한 번 열어야 유효하다. 없으면 조회는 SSE error로 실패(설계).
  • hsr-warp.exe, data/, config.json, *.tmp, 구 생성물 HSR_Warp_Dashboard.html은 gitignore 대상.
  • Go가 설치돼 있어도 PATH에 없을 수 있다. 그 경우 $env:Path에 C:\Program Files\Go\bin을 prepend.
  • 구 PowerShell 산출물 흔적: SRGF 파일의 선행 UTF-8 BOM을 readSRGF가 제거한다.
  • monthOf는 time 앞 7자(YYYY-MM)로 월 키를 만든다. 형식 불일치 레코드는 저장 시 조용히 건너뛴다.
