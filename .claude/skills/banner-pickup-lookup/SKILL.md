# 픽업 배너 라인업 조사와 반영

## 왜 이 작업이 까다로운가

50/50 판정은 "획득 시점에 그 아이템이 픽업이었나"로 결정된다(`web/analyze.js`의 `wasPickup`). 판단 근거는 `schedule.json`의 픽업 목록뿐이다. 그래서 목록이 불완전하면 **실제로는 픽승인 5성이 조용히 픽뚫로 집계된다.**

에러가 나지 않는다는 점이 핵심이다. 대시보드는 그럴듯한 숫자를 보여주고, 사용자는 승률이 낮다고만 느낀다. 게다가 픽뚫 판정은 `guaranteed` 상태를 세팅하므로 **다음 5성까지 확정으로 잘못 소비되는 연쇄 오류**가 난다. 한 건의 누락이 두 건의 통계를 망친다.

실제로 ZZZ 3.1 레미엘 배너에서 이 일이 있었다(이슈 #52). 배너 데이터 소스가 신규 배너의 픽업 id를 빈 채로 두고 이름과 기간만 담았고, 추출 스크립트는 그것을 "건너뜀"으로 처리하며 콘솔 경고만 남겼다. 그 경고는 스크립트 실행자에게만 보이고 앱 사용자에게는 그냥 틀린 숫자로 나타났다.

## 먼저: 두 실패 모드를 가른다

증상이 비슷해 보여도 원인과 고칠 위치가 전혀 다르다. **여기서 갈래를 잘못 잡으면 엉뚱한 파일만 고치고 증상은 그대로 남는다.**

| | A. 판정이 틀림 | B. 기록이 아예 없음 |
|---|---|---|
| 증상 | 그 배너 5성이 목록에 **있는데** 픽뚫·미확인으로 뜬다 | 그 배너에서 뽑은 것이 대시보드 어디에도 **없다** |
| 원인 | `schedule.json` 픽업 목록 누락 | 채널 코드가 수집 목록에 없어 요청조차 안 나감 |
| 고칠 곳 | `schedule.json` / 추출 스크립트 | `internal/game/game.go` + 채널 설정 일습 |
| 절차 | 아래 1~6단계 | **아래 "B 갈래"** |

가르는 방법은 하나다 — **그 배너에서 뽑은 기록이 저장돼 있는가.** 진단 스크립트의 `채널별 저장 현황`이 채널별 건수·최신 기록 시각을 보여준다. 기대하는 채널이 `0건`이거나 최신 시각이 그 배너 시작일보다 이르면 B다.

```bash
node .claude/skills/banner-pickup-lookup/scripts/diagnose-pickups.mjs <hsr|zzz>
```

사용자가 "조회가 안 된다"고 말해도 A일 수 있고, "판정이 틀렸다"고 말해도 B일 수 있다. **말이 아니라 저장 데이터로 가른다.**

## B 갈래 — 배너가 통째로 없을 때

기간 한정 특별 픽업 배너는 기존 채널과 **별개 코드**로 배포된다. 실제 사례: ZZZ 3.1 하반기 "3인 동시 특별 픽업"(다이아린·유즈하·하루마사)은 `real_gacha_type` `102`(에이전트)·`103`(W-엔진)으로 왔다. 앱이 아는 코드 목록에 없으면 그 채널로 **요청 자체를 보내지 않는다** — authkey 도 유효하고 조회도 성공하고 에러도 없다. 그래서 "그냥 안 뽑았나 보다"와 구분되지 않는다.

**1. 경계를 가른다.** 세 지점을 비교하면 어디서 끊겼는지 한 번에 나온다.

- `data/<game>/warp_YYYYMM.json` 의 최신 레코드 — 저장까지 왔나
- `/api/fetch?game=…&path=…` SSE 직접 호출의 `added` — 수집이 도는가
- `channelprobe` 응답 — API 에 원본이 있는가

**2. 채널 코드를 실측한다.** 추론하지 말고 두드린다.

```powershell
go run ./tools/channelprobe zzz 'D:\Game\HoYoPlay\games\ZenlessZoneZero Game' 1 2 3 5 102 103
```

- **한 자리 수에서 멈추지 않는다.** 기존 채널이 전부 한 자리라 1~13 만 훑고 끝내기 쉽다. 특별 채널은 100번대에 있다. 최소 `0~25`, `100~120`, `200~203` 은 훑는다.
- **그 배너가 진행 중일 때 훑는다.** 열리기 전에는 어떤 코드도 레코드를 주지 않으므로 "없음"이 거짓 음성이 된다.
- 소스의 `banner_type`(배너 분류)과 API 의 `real_gacha_type`(조회 코드)을 혼동하지 않는다. 값이 서로 다르다.

**3. 찾은 코드를 등록한다.** 손댈 파일 목록과 계정 전체 지표 합산 판단은 `docs/ARCHITECTURE.md` 의 "신규 가챠 채널이 열렸을 때" 표를 따른다. `npm test` 의 `banner-schedule.test.js`·`progress-map.test.js`·`i18n.test.js`·`nohardcode.test.js` 가 빠뜨림을 잡아준다.

**4. 등록 후 A 갈래로 넘어간다.** 채널이 붙으면 이제 그 기록들의 픽업 판정이 맞는지 확인해야 한다 — 라인업이 `schedule.json` 에 없으면 이번엔 전부 픽뚫로 뜬다.

## 작업 순서

> A 갈래(판정이 틀림) 절차다. B 를 먼저 처리했다면 이어서 여기를 밟는다.

### 1. 증상을 구체적으로 확보한다

사용자가 이름을 말했다면 그것이 가장 강한 단서다. 어떤 캐릭터·무기가, 어느 채널에서, 언제 뽑은 것이 틀리게 나오는지 확인한다. 사용자는 자기가 뽑은 것을 기억하므로 이 증언은 신뢰할 만한 근거다.

### 2. 진단 스크립트를 돌린다

```bash
node .claude/skills/banner-pickup-lookup/scripts/diagnose-pickups.mjs <hsr|zzz>
```

저장된 기록으로 분석을 돌려 픽뚫·미판정 5성을 그 시각의 픽업 목록과 나란히 보여준다. 전 5성을 보려면 `--all`을 붙인다.

스크립트가 **자동으로 판정하는 것**은 두 가지뿐이다. 이것들은 외부 지식 없이 확실하다.

- 픽업 배열(`c`/`l`)이 빈 구간 — 소스가 데이터를 못 채운 흔적
- 일정 마지막 종료일 이후에 획득한 5성 — 신규 패치 미반영

**픽뚫이 실제로는 픽업이었는지는 자동으로 알 수 없다.** 그 시기 공식 라인업을 알아야 하기 때문이다. 그래서 스크립트는 픽뚫을 단정하지 않고 대조표로만 보여준다. 사용자가 아는 신규 캐릭터가 그 목록에 있으면 그것이 누락 후보다.

### 3. 공식 라인업을 확인한다

**추론하지 않는다.** 사용자 증언은 출발점이지 최종 근거가 아니다. 다음 순서로 확인한다.

1. **게임별 데이터 소스** — `references/zzz.md` 또는 `references/hsr.md`에 소스 위치와 확인 방법이 있다. 소스가 이미 정보를 담고 있으면 스크립트 재실행만으로 끝난다.
2. **인게임 공시 원문** — ZZZ는 소스 repo에 배너별 공시가 들어 있다. 픽업 목록과 확률이 원문 그대로다.
3. **웹 검색** — 소스가 아직 수집하지 못한 신규 배너는 이 경로가 유일하다. 공식 배너 안내를 다루는 문서(게임 위키·공략 사이트)에서 **배너 이름과 기간**을 확인한다. 배너 이름이 중요한 이유는 소스가 이름은 맞게 담고 픽업 id만 비우는 경우가 있어, 이름으로 짝을 맞출 수 있기 때문이다.

한정 캐릭터에는 대개 전용 무기 배너가 함께 열린다. **둘 다 확인한다** — 하나만 고치면 다른 쪽이 계속 틀린다.

### 4. item_id를 확정한다

이름은 언어에 따라 다르지만 `item_id`는 불변이므로 이것이 실제로 반영할 값이다.

가장 확실한 근거는 **사용자의 실제 수집 데이터**다. API 응답의 `name`은 authkey의 `lang`을 따라 현지화되어 오므로, 한국어 이름으로 id를 되짚을 수 있다. 진단 스크립트가 픽업 목록의 id 옆에 이름을 함께 표시하는 것도 이 때문이다.

```bash
node -e "
const fs=require('fs');
const dir='data/zzz';            // hsr 이면 data/hsr
let all=[];
for(const f of fs.readdirSync(dir)) if(/^warp_\d+\.json$/.test(f))
  all.push(...JSON.parse(fs.readFileSync(dir+'/'+f,'utf8')).list);
for(const r of all) if(/레미엘/.test(r.name)) console.log(r.time, r.gacha_type, r.item_id, r.name, r.rank_type);
"
```

사용자가 그 아이템을 뽑지 않아 데이터에 없다면 게임별 아이템 id 사전을 참조한다(`references/`에 위치가 있다).

**id 자릿수로 종류를 교차 검증한다.** 두 게임 모두 캐릭터/에이전트는 4자리, 광추/W-엔진은 5자리다. 캐릭터 픽업(`c`)에 5자리가 들어가면 판정이 어긋나므로, 넣기 전에 자릿수를 확인한다.

### 5. 반영한다

반영 방법은 게임마다 다르다 — 작업 전에 해당 파일을 읽는다.

- **ZZZ**: `references/zzz.md` — 추출 스크립트가 소스에서 생성하므로 스크립트를 고친다. `schedule.json`을 직접 손으로 고치면 다음 재생성 때 사라진다.
  - **재생성은 산출물을 되돌릴 수 있다.** 소스(`zzz_formatted.json`)는 매일 갱신되며 **있던 항목이 사라지기도 한다** — 2026-08 실측에서 하루 전까지 있던 특별 채널(`banner_type` 12/13) 항목이 다음 날 통째로 없어져 37건 전부 `banner_type: 2` 였다. 재실행 전후로 `schedule` 길이와 최신 항목을 비교하고, 손으로 넣은 라인업이 날아가지 않았는지 확인한다. 사라졌다면 재생성분을 채택하지 말고 스크립트 안 상수로 고정한다.
- **HSR**: `references/hsr.md` — `web/schedule.json`을 직접 편집한다.

어느 쪽이든 **근거를 주석이나 커밋 메시지에 남긴다.** 나중에 소스가 갱신되면 이 보정이 필요 없어지는데, 근거가 없으면 지워도 되는지 판단할 수 없다.

### 6. 검증한다

수정 전후의 판정 변화를 실제로 비교한다. 숫자가 예상대로 움직이는지 확인하는 것이 이 작업의 완료 조건이다.

```bash
node .claude/skills/banner-pickup-lookup/scripts/diagnose-pickups.mjs zzz
npm test
```

**대시보드로 확인할 거라면 반드시 재빌드한다.** `web/` 아래 자산은 `go:embed`로 exe에 박히므로, 실행 중인 exe는 파일을 고쳐도 옛 화면을 계속 서빙한다. 브라우저 새로고침으로는 안 바뀐다 — "고쳤는데 그대로"의 대부분이 이것이다.

```powershell
go build -ldflags="-s -w" -o hsr-warp-debug.exe .
```

50/50 연쇄를 특히 확인한다. 픽뚫이 픽승으로 바뀌면 **그 다음 5성의 판정도 함께 바뀐다**(확정 소비가 사라지므로). 예를 들어 레미엘 케이스에서는 이렇게 바뀌었다.

```
수정 전: 레미엘 loss → 네코마타 guaranteed → 레미엘 loss
수정 후: 레미엘 win  → 네코마타 loss       → 레미엘 guaranteed
```

배너별 픽승/픽뚫/확정 수와 승률을 수정 전후로 나란히 보고한다. 사용자가 자기 기억과 대조할 수 있어야 한다.

## 하지 말 것

**모르는 값을 채우지 않는다.** 확인되지 않은 픽업을 추측으로 넣으면 틀린 판정이 "고쳐진 것처럼" 보여 더 나쁘다. 확인이 안 되면 확인이 안 된다고 말하고, 무엇을 확인해야 하는지 알린다.

**게임 버전 목록(`versions`)을 추측으로 채우지 않는다.** 버전 경계가 틀리면 버전별 통계가 조용히 왜곡된다. 일부만 아는 상태로 넣으면 빠진 구간이 앞 버전에 흡수되어 오히려 더 틀린다. 전부 확인하거나 비워 둔다.

**이전 커밋·PR의 "전수 확인했다"를 그대로 승계하지 않는다.** 단정의 **실측 범위**를 확인하기 전까지는 증거가 아니다. 실제로 #60은 "채널 코드를 실측으로 전수 스윕한 결과 2/3/1/5 외 어떤 코드도 레코드를 주지 않는다"고 커밋 메시지에 적었지만 훑은 범위는 1~13이었고, 그 결과 `102`/`103`을 놓쳐 기록 40건이 누락된 채 남았다. 그 단정이 지금 원인 후보를 **배제하는 데 쓰이고 있다면** 인용하지 말고 원래 범위 **바깥**을 직접 재실측한다.

**50/50 판정 로직(`wasPickup`, `guaranteed` 전이)은 건드리지 않는다.** 이 작업은 데이터를 고치는 것이지 판정 규칙을 바꾸는 것이 아니다. 판정이 틀려 보이는 원인은 거의 항상 데이터다.
